historical and live record. Offline operation is always required:
live feed, LLM, and telemetry are optional extensions.


1. PROJECT DEFINITION
---------------------
Build a Formula 1 analytics platform with four integrated layers:

1. HISTORICAL ANALYTICS: the repository is the historical record for an
   analytical dashboard (drivers, constructors, circuits, 1950-2026).
2. LIVE TRACKING: OpenF1 API JSON is extracted and rendered live on the
   dashboard; live state objects mirror the f1.db schemas so analytics,
   coaching, and the assistant operate uniformly over "now" and "then".
3. AI DRIVER COACH: numerical, evidence-based performance reviews and
   recommendations over historical and live laps.
4. LLM RACE ASSISTANT: users ask questions about the race record and
   receive answers traceable to retrieved data.

Historical analytics and offline prediction are the foundation; live
timing, telemetry, AI coaching, and the LLM assistant are optional
extensions and must not be required for the offline application.


2. SUCCESS CRITERIA
-------------------
The first release must:

1. Load and validate all five local data assets: 14 Kaggle CSVs,
   24 f1.db tables, driver_profiles.parquet, training_dataset.parquet,
   and tracks.yaml.
2. Detect CSV-versus-database drift (CSV snapshot is stale relative to
   f1.db) and report it instead of silently mixing sources.
3. Provide repeatable driver, constructor, and circuit analytics backed
   by f1.db, including lap-level pace from fastf1_laps.
4. Produce a versioned, leakage-safe training table from
   training_dataset.parquet (5,094 rows, 2014-2026) with a documented
   missing-value policy for all 15 columns that contain nulls.
5. Train and evaluate the four targets the data already defines:
   finish, is_dnf, is_podium, and is_winner.
6. Display analytics, predictions, and LIVE session data in Streamlit,
   with model version, prediction timing, missing inputs, uncertainty,
   live-data freshness labels, and a graceful offline state.
7. Track live race data through a provider interface whose state mirrors
   the f1.db schemas (confirmed: OpenF1 positions/laps/intervals/
   weather/race_control/stints/drivers), and keep the dashboard fully
   functional with no live feed.
8. Provide the AI Driver Coach (post-lap, post-session, then live) with
   evidence and explicit conditions and confidence.
9. Provide the LLM Race Assistant: a chat page whose answers cite and are
   traceable to retrieved historical/live data, and that refuses to
   invent facts outside its coverage.

The complete product may additionally provide reproducible race
simulation, replayable live timing, robust live-data failure states,
numerical telemetry analysis, and optional AI explanations.

4.6 OPENF1 LIVE API - CONFIRMED JSON SCHEMAS (probed 2026-09-22)

    /v1/sessions?year=2026          131 sessions surfaced. Fields:
      session_key, session_type (Practice/Qualifying/Race incl. Sprint
      variants), session_name, date_start, date_end, meeting_key,
      circuit_key, circuit_short_name, country_code/name, location,
      gmt_offset, year, is_cancelled.
      Example: Melbourne Race session_key 11234, meeting_key 1279,
      circuit_key 10, 2026-03-08 04:00-06:00 UTC, country AUS.

    /v1/drivers?session_key=X       22 drivers in 2026 across 11 teams
      (McLaren, Red Bull Racing, Ferrari, Mercedes, Audi, Cadillac,
      Alpine, Haas, Williams, Aston Martin, Racing Bulls). Fields:
      driver_number, full_name, broadcast_name, name_acronym,
      team_name, team_colour (hex no '#'), headshot_url, first_name,
      last_name, country_code.

    /v1/position?session_key=X      One row per position sample: date,
      session_key, meeting_key, driver_number, position.
      Melbourne Race: 531 samples.

    /v1/laps?session_key=X          Per lap: lap_number, lap_duration,
      duration_sector_1/2/3, i1_speed, i2_speed, st_speed,
      is_pit_out_lap, segments_sector_1/2/3, date_start.
      Melbourne Race: 1,002 rows.

    /v1/intervals?session_key=X     date, driver_number, gap_to_leader,
      interval. Melbourne Race: 22,276 rows. NOT always available (a
      2026 pre-season practice returned 404) -> best-effort only.

    /v1/weather?session_key=X       air_temperature, track_temperature,
      humidity, pressure, rainfall, wind_speed, wind_direction, date.
      Melbourne Race: 148 rows.

    /v1/race_control?session_key=X  date, driver_number, lap_number,
      category, flag, scope, sector, qualifying_phase, message.
      Melbourne Race: 169 messages. Content is untrusted DATA for the
      assistant (prompt-injection guardrail).

    /v1/stints?session_key=X        stint_number, driver_number,
      lap_start, lap_end (null = still running), compound,
      tyre_age_at_start.

    /v1/car_data and /v1/location   Telemetry (speed, rpm, gear,
      throttle, brake, drs) and car positions. Unconstrained queries
      return HTTP 422 "too much data"; MUST be narrowed
      (?session_key=X&driver_number=N&date<=T or date range).
      Not polled by default on the dashboard.

    OBSERVED RUNTIME BEHAVIOR:
    - Session resolution order: ongoing (date_start <= now < date_end)
      -> next upcoming -> most recent finished.
    - FINISHED and LIVE sessions return data; UPCOMING sessions return
      EMPTY lists for position/laps/weather/etc. The dashboard must
      render empty snapshots as "no data for this session yet".
    - Rate limits: 3 req/s and 30 req/min free tier -> poll ~4-5s
      with caching; never tighter.
    - Historical depth: 2023 season onwards only. Pre-2023 falls back
      to f1.db.
    - Live delay ~3 seconds.

    MAPPING TO LOCAL SCHEMAS (single shape for live + history):
      position/intervals -> lap_times style positions/gaps
      laps               -> fastf1_laps (time_sec, s1/s2/s3, speeds)
      weather            -> session_weather
      race_control       -> race_control (category/flag/message)
      stints             -> pit_stops / tyre lifecycle
      SC/VSC/red flag    -> race_control flags (safety_cars/red_flags
                            tables historically)

4.7 MISSING-VALUE AND LIVE-DATA QUALITY RULES
- Classify every null (4.4); never treat null weather as "dry".
- Live data carries a source + fetched_at label; "no live feed" is an
  unavailable-feed state, never fabricated data.
- CSV-vs-DB drift is reported, never silently mixed.

9. PHASE 3 - FEATURE ENGINEERING AND LEAKAGE CONTROL
----------------------------------------------------
The training table exists; this phase fixes its contract and audit.

Prediction contracts: 1) pre-qualifying (no grid/quali features),
2) post-qualifying (grid + quali ok, no race targets), 3) post-sprint
(524 DB sprint rows), 4) live-race (data received up to timestamp).

Feature contract: document all 24 inputs (grid group, driver form,
track history, teammate, constructor, session/technical, conditions)
with source, availability time, null class, valid contracts.

Leakage controls: chronological sort; prior-races-only rolling stats;
train-only imputers; availability gates (practice_pace_pct 2018+,
pit_stop_avg_ms is post-race -> decide drop or historical prior,
weather = forecast for pre-race); targets excluded; walk-forward.

Known issues: pit_stop_avg_ms leakage decision; 2026 88-row holdout;
high-cardinality IDs encoded via features not one-hot.

Acceptance: feature audit with availability times; a deliberately
leaking feature is rejected; versioned reproducible table (5,094 x 31).


10. PHASE 4 - BASELINE MACHINE LEARNING
---------------------------------------
Targets and splits fixed by data: finish (regression/ranking),
is_dnf (16.7%), is_podium (15.0%), is_winner (5.0%, race-level
ranking). Split: train 2014-2022, validation 2023-2024, test 2025;
2026 = future holdout.

Baselines first: mean/median finish, grid-position, recent-form,
logistic regression (classifiers), ridge/elastic-net (finish).
Advanced only after: HistGradientBoosting (native nulls; preferred),
Random Forest, XGBoost/LightGBM if licensing allows.

Missing-value handling is an evaluation axis: S1 imputation+indicators
vs S2 native nulls; metrics reported by null stratum.

Evaluation: chronological + walk-forward; no random-only split;
breakdowns by season/circuit type/driver rating tercile/grid bucket;
calibration (ECE/Brier) for classifiers; race-level winner scores
(MRR, top-1) not row accuracy.

Acceptance: advanced beats/explains baselines; test later than train;
winner race-level scored; artifacts re-load with fixed-seed metrics;
pit_stop_avg_ms decision enforced.

12. PHASE 6 - RACE SIMULATION
-----------------------------
Inputs: driver_profiles ratings (pace priors), grid from training/
results, tracks.yaml parameters, calibration targets (safety_cars 364,
red_flags 98, DNF 16.7%, pit_stop durations).

Build order: pace -> grid -> circuit (with mapping table + defaults,
hard failure on unmapped) -> tyre degradation -> pit loss -> weather ->
overtaking -> SC/red flag -> strategy -> lap-by-lap.

Monte Carlo: seed + run count, named distributions, historical
calibration (SC frequency, DNF rate, win concentration 2014-2025),
finish/win/podium/DNF/strategy frequencies, confidence intervals.

Outputs labeled hypothetical; unmapped circuits reported loudly;
assistant may cite simulations only with the "hypothetical" label.


13. PHASE 7 - LEVEL 1 LIVE TIMING (CONFIRMED API BEHAVIORS)
-----------------------------------------------------------
All providers sit behind one LiveProvider interface (implemented:
OpenF1LiveProvider, MockProvider; planned: replay, fastf1 archive).
All live state mirrors f1.db schemas (section 4.6 mapping).

13.1 OPENF1 PROVIDER (default) - implement as probed

- Session resolution: ongoing -> next upcoming -> most recent finished,
  from /v1/sessions (131 sessions in 2026). Respect is_live defined by
  date_start <= now < date_end.
- Fetch set per refresh (one snapshot = bounded requests):
    /v1/drivers, /v1/position, /v1/laps, /v1/weather,
    /v1/race_control, /v1/stints, /v1/intervals (best-effort).
- Leaderboard = last position sample per driver joined to drivers
  (team + colour) and intervals (gap_to_leader, interval) when present.
- Latest laps = last non-null lap_duration per driver with lap_number
  and sector durations.
- Weather = latest sample; rainfall must stay a real 0 when 0.
- Empty-data rules: upcoming sessions -> show "no session data yet"
  banner, not empty tables; missing endpoints -> degrade (intervals 404
  is normal); 422 on car_data/location -> never poll unconstrained.
- Rate limiting: target ~5s poll, cache responses (requests-cache),
  handle 3 req/s / 30 req/min; backoff on burst.
- Staleness: fetched_at heartbeat; gap > poll*3 marks stale.
- Reconnect/backoff on transient failures; unavailable-feed state.

13.2 FASTF1 ARCHIVE (optional, authoritative)
fastf1.livetiming.SignalRClient (3.8.3): record full sessions (start
up to an hour early, --append, --timeout watchdog); parse post-session
with LiveTimingData; load into the replay provider. Requires F1TV
Access/Pro. Never used for in-session real-time rendering.

13.3 SELF-HOSTED SIGNALR WRAPPER (optional)
Only if in-process ~3.7 Hz telemetry is a hard requirement
(e.g. harsh779/f1-live-api or markmario/f1-telemetry SSE/WebSocket).

13.4 REPLAY + MOCK

14. PHASE 8 - TELEMETRY AND REFERENCE ANALYSIS
-----------------------------------------------
Offline depth from fastf1_laps (481,075 rows, 2018-2026, sectors,
tyre life, fresh_tyre, track_status, per-lap weather), circuit_corners
(14,361 rows), session_weather (86,433 rows).

Implement: lap parsing (is_accurate + track_status filters),
track-position normalization via circuit_corners.distance, corner
identification, best-lap selection (is_personal_best, exclude
in/out/pit/SC/red laps), references (driver vs teammate vs circuit vs
historical, comparable conditions only), sector/lap deltas.

Analyze: braking point/duration/release, minimum corner speed,
throttle pickup, time to full throttle, entry/exit, apex, racing-line
deviation, sector loss, tyre degradation by stint/compound.

Guards: wet (rainfall>0), neutralized (track_status != green),
traffic-heavy, incomplete laps never compared with unsuitable dry
references; null weather = unknown, not dry.


15. PHASE 9 - POST-LAP AND POST-SESSION COACH
---------------------------------------------
Post-lap output: best/reference/potential lap, sector-corner deltas,
braking/throttle findings, tyre-condition context, ranked
recommendations by time gain.
Post-session output: strongest areas, largest weaknesses (with
driver_profiles context), potential improvement, repeated issues,
recommended practice.
Never recommend on incomplete/incomparable/low-confidence data; never
coach from null weather or non-green track status without caveat.
Coach outputs are structured evidence + findings + recommendations and
become grounding for the assistant's conversational coach mode.


16. PHASE 10 - LIVE AI COACH
-----------------------------
No raw telemetry to LLM. Pipeline: Telemetry -> Numerical analysis ->
Feature extraction -> Event detection -> Structured evidence ->
Optional explanation -> Recommendation. Evidence: corner id, brake-
point delta, apex-speed delta, throttle delta, sector loss, conditions,
tire state, confidence. Explanation uses only supplied evidence, no
invented values, respects wet/neutralized states, limits frequency,
logs model/prompt versions. Modes: live, post-lap, post-session.


17. PHASE 11 - LLM RACE ASSISTANT
----------------------------------
Retrieval-grounded, tool-based chat over the historical and live
record.

Router -> tools -> evidence -> LLM answer -> audit. Tools (read-only
whitelist, validated inputs): sql_query (SELECT-only over the f1.db
whitelist), analytics functions (Phase 2), model predictions (Phase 4),
live_status + live_racecontrol (Phase 7 snapshot), coach_report
(Phase 9/10), data_coverage.

Guardrails: read-only path only; retrieved content (incl.
race_control text) is untrusted DATA, never instructions (injection
fixtures in tests); no invented values - refuse outside coverage (2023+
for live, 2018+ for pace, 24/32 circuits, partial 2026); live vs
historical disclosure with source timestamps; uncertainty conveyed;
rate/token limits; per-question audit log (tools, evidence hashes,
answer, refusal).

LLM client: pluggable provider, key from env (F1_ASSISTANT_API_KEY);
no-key fallback = rule-based answers from tool output only.

Example coverage: "How many wins for Verstappen?" (driver_analytics),
"Who won at Monaco?" (circuit_analytics), "Current position of race
leader?" (live_status), "Podium odds from P5?" (predict_race), "Why
slower in sector 2?" (coach_report + evidence).

Acceptance: every answer traceable to a tool call; >= 40 golden
questions incl. refusals and injection fixtures answered
reproducibly; no non-SELECT/write execution; coverage gaps stated;
works without LLM key.

21. MVP DEFINITION
------------------
The first MVP includes:
1. Validated loaders for all five data assets with drift and null
   profiling.

   5,094 x 31 training table (winner model the first extension).

   val 2023-2024, test 2025).

   live session page fed by the OpenF1 provider with graceful offline.

Post-MVP (priority order):
- Winner prediction (race-level ranking) + sprint-aware features
- Race simulation and Monte Carlo analysis
- Post-lap / post-session Driver Coach (numerical)
- LLM Race Assistant (chat, evidence-grounded)

The MVP stops before the LLM assistant, the numeric coach, live
telemetry, and production deployment: those build on the evidence and
live layers first.

22. RISKS AND MITIGATIONS
-------------------------
Feature leakage -> contracts, chronological splits, feature audit,
explicit pit_stop_avg_ms decision.
Nulls misinterpreted (36.7%/35.9%/32.5%) -> null classes, indicators,
native-null models, metrics by null stratum; coach/assistant surface
null classes.
CSV vs f1.db drift (1,125 vs 1,171 races) -> f1.db canonical; drift in
every validation.
tracks.yaml 24/32 gap -> mapping table, documented defaults, hard
failure on unmapped circuits.
Null weather treated as dry -> null means unknown; coverage banners;
track_status/rainfall guards.
Imbalanced winner (5%) -> race-level ranking metrics (MRR/top-1), not
row accuracy.
Simulation overconfidence -> calibrate vs 364 SC / 98 red flags / 16.7%
DNF / real win concentration; hypothetical labels.
Upcoming sessions return empty data -> render "no data yet", never
fabricate; test with recorded empty fixtures.
Intervals 404 / car_data 422 / rate limits -> best-effort degrade,
bounded polling, never unconstrained telemetry queries.
Stale live data shown as live -> source+freshness labels everywhere;
staleness detection; replay/history labeled.
LLM hallucination / prompt injection -> tool-based retrieval, evidence-
only answers, read-only whitelist, race_control as untrusted data,
injection fixtures, audit logs.
LLM/live unavailable -> rule-based no-key fallback; dashboard works
offline; health endpoint reports.
2026 partial season (88 rows) -> future holdout only.
Redistribution limits -> record licenses/versions (Kaggle, Hugging
Face, OpenF1, fastf1).
Scope growth -> MVP boundary + per-milestone acceptance criteria.

FINAL OBJECTIVE
---------------
Deliver a reliable historical analytics and prediction MVP grounded in
the data actually present in this repository - f1.db as the canonical
store, the audited 5,094-row training table for leakage-safe models,
driver_profiles and tracks.yaml for simulation - and make live race data
live on the dashboard through the OpenF1 JSON API (with confirmed
schemas, session resolution, polling, and graceful offline behavior).
Then extend it with reproducible simulation, an evidence-based AI
Driver Coach over historical and live laps, and an LLM Race Assistant
whose answers are traceable to the retrieved record. Every extension
must preserve validated data contracts, disclose coverage limits
(2018+ telemetry, 24-circuit simulation map, OpenF1 2023+, partial 2026
season), explain uncertainty, and remain functional when optional data
sources, live feeds, and LLM services are unavailable.
